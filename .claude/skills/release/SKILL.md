# AI Radio リリース作業

このスキルは、機能追加やバグ修正がある程度まとまって「安定した」タイミングで、
バージョン番号を上げてリリースコミット＋タグを作成する一連の作業を行う。
このリポジトリでは `v1.0.0` 以降、`release: Version X.Y.Z — <概要>` という形式の
コミットと、対応する注釈付きタグ（`vX.Y.Z`）を作り続けてきた（`git log --oneline` で確認可能）。
この形式・粒度を壊さず踏襲することが目的。

**このワークフローは実際にリポジトリへコミット・タグを作成する。** 新しいバージョン番号と
チェンジログ文面は必ずユーザーに提示し、明示的な了承を得てから git 操作に進むこと
（黙って決め打ちしない）。push は絶対に自動で行わない。

## 引数（バージョン番号の指定方法）

`/release` の後に任意で引数を渡せる。渡し方によって手順2（バージョン番号決定）の
挙動が変わる:

- **`/release`（引数なし）** — 変更内容から minor/patch を提案し、会話の中で確認する
- **`/release 1.7.0`（具体的なバージョン番号）** — その番号を使う。ただし妥当性
  （現在のバージョンより大きいか、規模感と釣り合っているか）は一声確認してから進める
- **`/release minor`** / **`/release patch`** — 上げ幅だけを指定。現在のバージョンに
  対してその桁を1つ上げた番号を算出して提示する（例: 現在 1.6.0 で `patch` 指定なら 1.6.1）

いずれの場合も、最終的なチェンジログ文面と確定したバージョン番号は手順3の下書き提示時に
ユーザーへ見せて了承を得ること。引数で番号を渡されたからといって確認を省略しない。

## 手順

### 1. 前回リリース以降の変更点を把握する

```bash
git describe --tags --abbrev=0          # 直近のタグ（例: v1.6.0）を取得
git log <直近タグ>..HEAD --oneline       # タグ以降のコミット一覧
git diff <直近タグ>..HEAD --stat         # 変更ファイル一覧（規模感の把握）
git status --short                       # 未コミットの変更・未追跡ファイル
```

タグが1つも無いリポジトリ状態なら `git log --oneline` で全履歴を確認する。

未コミットの変更がある場合（このセッションで作業した変更など）は、それも含めて
今回のリリースに入れるべきかユーザーに確認する。無関係な作業中のファイルが混ざっている
可能性があるため、`git add -A` や `git add .` は使わず、リリースに含めるべきファイルを
明示的にパスで指定して `git add` すること。

`.gitignore` に含まれるファイル（例: `server/data/channels/*/played_tracks.json`、
`server/data/channels/*/long_term_memory.json`、`server/data/credentials.json` など）は
リポジトリの実データ・認証情報であり、絶対にコミットに含めない。ディレクトリ単位で
`git add <dir>/` すれば `.gitignore` は自動的に尊重されるが、`git status --short` の
結果で意図しないファイルが紛れ込んでいないか一度目視確認する。

### 2. 新しいバージョン番号を決める

このリポジトリはセマンティックバージョニングに近い運用をしている:
- 新チャンネル・新モード・大きな新機能の追加 → **minor** を上げる（例: 1.5.2 → 1.6.0）
- バグ修正・品質改善・小さな機能追加のみ → **patch** を上げる（例: 1.5.0 → 1.5.1 → 1.5.2）

引数が無ければ、集めた変更点の性質から次のバージョン番号を提案し、必ずユーザーに確認する。
引数で具体的な番号（例: `1.7.0`）が渡されていればそれを使い、`minor`/`patch` のような
上げ幅指定であれば現在のバージョン（`package.json` の `"version"`）から算出する。
過去の判断に迷う場合は素直に「minorとpatchどちらにしますか」と聞けばよい。

バージョンが影響する箇所:
- ルートの `package.json` の `"version"`
- `client/package.json` の `"version"`
- `README.md` 1行目のタイトル `# 私だけの AI Radio 🎙️ — vX.Y.Z`

`server/package.json` の `"version"`（現在 `1.0.0` 固定）はこのバージョニング体系に
含まれていないため**触らない**。

### 3. RELEASENOTE.md のチェンジログ下書きを作成する

バージョンごとの変更履歴は `README.md` からは分離済みの `RELEASENOTE.md` に一元管理している
（`README.md`側には「リリースノート」セクションから`RELEASENOTE.md`へのリンクのみが残る）。
`RELEASENOTE.md`は新しいバージョンが常に一番上に来る降順の変更履歴になっている。過去の
エントリ（例: v1.10.1, v1.10.0, v1.9.1 …）を読んで、以下の形式を寸分違わず踏襲すること:

```markdown
## vX.Y.Z <2〜3語程度の日本語サマリー>（YYYY-MM-DD）

- [x] **<太字の短い見出し>** — <何を・なぜ・どう直したか、を1〜3文で具体的に。
      ファイル名やメソッド名など固有名詞を含めると後から読んだときに追跡しやすい>
- [x] **<次の変更点>** — ...
```

（`RELEASENOTE.md`内はバージョン見出しが`##`である点に注意。`README.md`側の見出し階層と
異なるので、そのまま転記せず見出しレベルを揃えること。）

各箇条書きは「1コミットの塊」ではなく「ユーザーや開発者にとって意味のある変更単位」で
まとめる（例: 複数ファイルにまたがる1つのバグ修正は1箇条にまとめる）。
`git log` のコミットメッセージと `git diff --stat` から変更の実体を確認しながら書くこと。
コミットメッセージをそのまま転記するのではなく、変更の背景（なぜ壊れていたか／なぜ必要か）
まで一段掘り下げて書くのが、このRELEASENOTE.mdの既存エントリのスタイル。

日付は今日の日付（YYYY-MM-DD形式）を使う。

**下書きができたら、新バージョン番号とこのチェンジログ文面をそのままユーザーに提示し、
「この内容でコミットしてよいか」を確認する。** ユーザーが修正・追加・削除を指示したら
反映してから次に進む。

### 4. README.md のリファレンス内容が最新か確認する

`README.md` はチェンジログ（`RELEASENOTE.md`に分離済み）とは別に、目次にある各セクション
（アーキテクチャ図・エージェント構成表・外部API連携・ディレクトリ構成・セットアップ・
設定ファイル・管理画面・AI Radio Information Service・WebSocketイベント仕様・音声パイプライン・
オーディオミキサー構成・TTS発音正規化・ログ）がプロジェクトの**現在の実態を説明するリファレンス**
になっている。バージョン番号だけ上げてこれらを放置すると、コード側は先に進んでいるのに
README側の説明が古いまま、という乖離が積み重なっていく。**このリファレンス内容も、
機能追加・変更があれば毎回このタイミングで見直し、必要なら更新する。**

手順1で集めた `git log`/`git diff --stat` の内容から、以下のような兆候がないか確認する:

- 新しいエージェント・チャンネルの追加/削除 → 「エージェント構成」の表、「アーキテクチャ」図中の
  WebSocketエンドポイント一覧、「ディレクトリ構成」のファイルツリーに反映が必要か
- 新しい外部API・データソースとの連携 → 「外部API連携」のテーブルに追加が必要か
- 新しいREST APIエンドポイント・`config.json`のフィールド追加/変更 → 「設定ファイル」のJSON例、
  「管理画面」の説明に反映が必要か
- WebSocketイベントの追加・変更・廃止 → 「WebSocketイベント仕様」セクション
- 音声パイプライン・オーディオミキサーのロジックに構造的な変更 → 該当セクション
- セットアップ手順（必要なツール・環境変数・起動コマンド等）に影響する変更 → 「セットアップ」

該当しそうな兆候が見つかったら、そのセクションを実際に読んでから修正案を作成する
（想像で書かず、現在のコード・設定ファイルの実態を確認すること）。修正案は手順3の
チェンジログ下書きと合わせてユーザーに提示し、「この内容で反映してよいか」を確認する。

該当する変更が今回の差分に見当たらない場合は、無理に何かを書き換える必要はない。
その場合は「今回はREADME.mdのリファレンス内容に構造的な更新は不要と判断しました」と
一言添えてユーザーに伝え、次の手順に進む。

### 5. README.md・RELEASENOTE.md・package.json を更新する

- `README.md` 1行目のバージョン番号を書き換える
- 手順4で承認された更新箇所があれば、該当セクションに反映する
- `RELEASENOTE.md` の先頭（既存の一番上のエントリより前、イントロ文の直後）に、確認済みの
  新エントリを`## vX.Y.Z ...`見出しで挿入する
- ルート `package.json` と `client/package.json` の `"version"` を書き換える

### 6. コミットする

```bash
git add <対象ファイルを明示的に列挙>
git commit -m "$(cat <<'EOF'
release: Version X.Y.Z — <チェンジログと同じ日本語サマリー>

<必要であれば1〜3行の補足説明>

Co-Authored-By: Claude Sonnet 5 <noreply@anthropic.com>
EOF
)"
```

コミットメッセージの1行目は必ず `release: Version X.Y.Z — <概要>` の形式にする
（過去のリリースコミットと同じ検索性・一貫性を保つため）。
`--no-verify` などでフックをスキップしない。pre-commit フックが失敗した場合は
原因を直してから新しいコミットとしてやり直す（`--amend` はしない）。

### 7. 注釈付きタグを作成する

```bash
git tag -a vX.Y.Z -m "Version X.Y.Z — <チェンジログと同じ日本語サマリー>"
```

### 8. クライアントを再ビルドする

```bash
npm run build --prefix client
```

**この再ビルドは、クライアント側の変更の有無にかかわらず毎回必ず行うこと。**

理由は2つある。

**① バージョン番号はビルド成果物に焼き込まれる。** `client/vite.config.ts` は
`__APP_VERSION__: JSON.stringify(process.env.npm_package_version)` として、
**ビルド時点の `client/package.json` の値**をバンドルへ埋め込む（画面右下の
「AI Radio Version X.Y.Z Build: <hash>」表示、`client/src/Player.tsx`）。
つまり `client/package.json` を書き換えただけでは画面のバージョンは変わらず、
再ビルドして初めて反映される。`__BUILD_HASH__`（`git rev-parse --short HEAD`）も同様で、
リリースコミットの後にビルドしないと1つ前のハッシュが残る。

**② 配信される実体は `client/dist` であり、git 管理外。** `server/routes/static-routes.js`
（`registerStaticRoutes`）は `client/dist`（Viteのビルド成果物）を静的配信しており、
`server/server.js` はソースを直接見ない。`client/dist` は `client/.gitignore` で
git 管理外のため、**バージョン管理側（コミット・タグ）が最新でも、ローカルの
`client/dist` が古いままだと配信される実体は古いバンドルのまま**という乖離が静かに残る。

**過去に2回、実際に事故になっている**:
- 2026-08-15（音声ミキサー24kHz移行）: サーバーだけ再起動してもオープニングBGMの
  サンプリングレートが直らず、原因調査の末に `client/dist` が前日のビルドのまま
  取り残されていたと判明
- 2026-09-06（v2.0.0）: 「今回は `client/src` に変更が無いので再ビルド不要」と判断した結果、
  画面のバージョン表記が更新されず指摘を受けた。**バージョン番号自体が
  ビルドに焼き込まれることを見落としていた**のが原因。この条件分岐そのものが誤りだった

**ビルド後は、実際に埋め込まれた値を必ず確認すること**（「ビルドが成功した」だけでは
バージョンが入った証拠にならない）:

```bash
grep -oh 'Version `,`[0-9.]*`,`.\{0,30\}' client/dist/assets/main-*.js
git rev-parse --short HEAD    # 上の Build ハッシュと一致するか
```

minify 後はダブルクォートではなくバッククォートになるため、`grep '"2.0.0"'` のような
探し方では見つからない点に注意する。

### 9. 結果を確認してユーザーに報告する

```bash
git log --oneline -1
git tag --list | tail -5
```

コミットハッシュとタグ名をユーザーに報告する。**この時点ではリモートに push しない。**
push が必要かどうかは必ずユーザーに尋ねてから行う。

手順8の再ビルドを行った旨と、埋め込まれたバージョン・ビルドハッシュを併せて報告し、
**今動いているサーバープロセスの再起動・ブラウザのハードリロードが必要になる可能性が
あることを伝える**（実際に再起動するかどうかは、放送中・会話中の可能性を考慮して必ず
ユーザーに確認してから行う——このワークフロー自体が自動でサーバーを再起動することは
絶対にしない）。

## やってはいけないこと

- コミット・タグを作る前にユーザーへ内容確認せずに進めること
- `git add -A` / `git add .` で無関係な変更まで巻き込むこと
- `.gitignore` されているデータ・認証情報ファイルをコミットに含めること
- `server/package.json` のバージョンを変更すること
- 確認なしに `git push` すること
- 確認なしに稼働中のサーバープロセスを再起動すること（放送・会話中の可能性があるため）
- 手順8の再ビルドを省略すること（`client/src` に変更が無い回でも必ず行う。バージョン番号と
  ビルドハッシュはビルド時にバンドルへ焼き込まれるため、省くと画面の表記が古いまま残る。
  2026-09-06 の v2.0.0 で実際に発生した）
- 「ビルドが成功した」ことだけを確認して、埋め込まれたバージョンを確かめずに報告すること
- エージェント名をプロンプト文字列にハードコードするような変更（`CLAUDE.md` 参照）——
  このスキル自体はバージョン表記・README.md・RELEASENOTE.mdしか触らないため通常は無関係だが、
  リリース対象の差分にエージェント名ハードコードが混ざっていないか気づいたら指摘する
