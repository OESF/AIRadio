# ソースコメントの JSDoc 整理

ソースのコメントを CLAUDE.md「7. コメントの書き方（JSDoc）と整理の進め方」の決まりに
書き直す作業を、1回分の量（行数）だけ進める。**コードは1文字も変えない**。コメントと空白だけを変える。

## 引数

- **`/doc-cleanup`（引数なし）** — 予算 2,000 行
- **`/doc-cleanup 1500`（数字）** — 予算をその行数にする
- **`/doc-cleanup server/routes`（フォルダー）** — そのフォルダーの未整理ファイルから、予算 2,000 行分
- **`/doc-cleanup server/lib/foo.js`（ファイル）** — そのファイルだけ（大きければ予算分の範囲だけ）
- フォルダー・ファイルと数字は併用できる（例: `/doc-cleanup server/routes 1000`）

## 手順

### 1. 対象を選ぶ

```bash
node scripts/doc-progress.js
git status --short
```

- **途中のファイル（`@doc-partial`）があれば、それを最優先で続ける**。
- 次に、未整理のファイルを**行数の少ない順**に取り、合計が予算に収まるところまで選ぶ。
- 次のファイルを足すと予算を超える場合:
  - まだ1本も選んでいなければ、そのファイルを予算分の範囲だけ進める（手順5の「途中で止める場合」）。
  - 1本以上選んでいれば、そこで止める。
- **未コミットの変更があるファイルは選ばない**（手順4の比較が HEAD を基準にするため、
  コメント以外の作業中の変更と区別できなくなる）。
- 選んだファイルと合計行数を、作業の前に一言伝えてから進める（確認待ちはしない）。

### 2. 読んで理解する

ファイル全体を読み、「何を処理するファイルか」「誰から使われるか」（`git grep -l "<ファイル名>')"`）、
「どこにデータを保存するか」を把握する。経緯のコメントは、判断の材料として読む。

### 3. 書き直す

CLAUDE.md 7節の決まりに従う。要点:

- **ファイルヘッダー**: `@file`（1行で何を処理するか）、概要（仕組み・主な利用元・保存先）、
  `@author` 3行、`@copyright`、`@license MIT`、`SPDX-License-Identifier: MIT`、`@doc-reviewed <今日の日付>`。
  `'use strict';` はヘッダーの**後**に置く（既存の位置から動かすのは空白とコメントの移動なので問題ない）。
- **関数**: 1行の要約、`@param`（全引数）、`@returns`。JS ファイルでは型も書く。
  TS/TSX ファイルでは型はコードにあるので、JSDoc には説明だけを書く（`@param name 説明`）。
- **行内のコメント**: 「なぜそうしているか」だけを残す。コードを読めば分かる「何をしているか」は削る。
- **経緯を消す**: 日付・「三浦さんのご指示」・「第◯段」・IDEA.md の番号・バグ調査の物語は削る。
- **経緯の中の知見はタグで残す**:
  - `ATTENTION:` … 守らないと壊れる制約、やってはいけない操作
  - `BUGFIX:` … 過去のバグの再発防止のためにこうなっている（消すと再発する）
  - `TODO:` … やり残し・将来やること
  - `FIXME:` … 分かっているが未修正の不具合
  既存の `TODO` も、この形（`TODO:`）にそろえる。
- **エージェント名**: コメントでも、設定で変わる名前（MAX・Clara など）より役割名（キャスター・アシスタント）で書く。
- 書き直しは**1ファイルずつ Write で丸ごと**書くのが確実。ただし数千行のファイルは Edit で区間ごとに行う。

#### やってはいけないこと
- コードを変えること（変数名の変更・整形・リファクタ・バグ修正も含む）。気づいたバグは `FIXME:` を
  書いて報告に挙げるだけにする
- テンプレートリテラル（プロンプト文字列）の中を変えること。`//` や `/*` がテンプレートの中にあっても、
  それはコメントではなく文字列
- JSDoc の型のために、コードへ括弧やキャスト（`/** @type */ (x)`）を足すこと（字句が変わる）
- JSX の中に新しいコメント `{/* … */}` を足すこと、既存のものを消すこと（`{` `}` が字句として増減する）。
  JSX 部分への注意書きは、コンポーネントの JSDoc に書く。既存の JSX コメントは中の文だけを書き換える
- `/* … */`・`/** … */` のコメントの本文に `*/` を書くこと（そこでコメントが終わり、残りがコードになる）。
  `{/* */}` のような記法をコメントの中で説明したいときは、言葉で書く（「波かっこで囲んだ JSX のコメント」）

### 4. 確かめる

```bash
node scripts/doc-verify.js <file1> <file2> ...
```

全ファイルが「✓ コードは同一」になること。「✗」が出たら、表示された位置を見て元に戻す。

型の指摘が増えていないかも比べる。

- **サーバー側の JS**: 整理前（HEAD）と整理後の指摘を比べる。
  ```bash
  node scripts/doc-typecheck.js <server の file1> <file2> ...
  ```
  - 増えた指摘が、自分が書いた JSDoc の型の誤りなら、型の書き方を直す（コードは変えない）。
    よくある原因: `{object}` と書くとプロパティが無い型になる（`{Record<string, any>}` にする）、
    `@type` を付けた変数が null を取りうるのに、非 null を返す関数の戻り値に使われている。
  - エラー文の中の型の表記が変わっただけ（同じ種類の指摘の出入り）なら問題ない。整理前の同じファイルの
    指摘と見比べて確かめる。
- **クライアント側の TS/TSX**: プロジェクトの設定で検査し、指摘が0件のままであること。
  ```bash
  (cd client && node_modules/.bin/tsc -b --noEmit)
  ```
- 最後に、サーバー側の JS を読み込めることを確かめる（読み込むと起動処理が走るファイル
  — server.js など — は除く）: `node -e "require('./<file>')"`

### 5. 途中で止める場合（大きいファイル）

予算内に収まらない大きいファイルは、先頭から予算分の範囲だけ整理する。

- 初回にファイルヘッダーを書く。ヘッダーには `@doc-reviewed` の代わりに、どこまで進めたかを書く:
  `@doc-partial <今日の日付> <最後に整理した関数名やセクション名>まで`
- 2回目以降は、`@doc-partial` の続きから進め、この行を更新する。
- 最後まで終えたら `@doc-partial` の行を `@doc-reviewed <日付>` に置き換える。

### 6. 報告する

- 整理したファイル（行数）、`doc-verify` の結果、型検査の結果（件数の増減）
- 書き直した ATTENTION / BUGFIX の件数と、特に重要なもの（あれば）
- コメントを読んで気づいた、コードのバグらしきもの（`FIXME:` を書いたもの）
- `node scripts/doc-progress.js` の先頭（全体の進み具合）
- 残りの目安（未整理の行数）

**コミットはしない**（ユーザーが「コミットまで」と言った場合だけ、整理したファイルだけを明示的に
`git add` してコミットする。メッセージは `docs: <対象> のコメントを JSDoc に整理` の形）。
サーバーの再起動は不要（コメントしか変わっていないため）。
